# Rosen Ergo-side bridge evidence

Decoder v1 follows native ERG requests in the exact Rosen public-launch **7.1.1** lock contract, with no other tokens in the deposit, to Cardano, Ethereum or Binance. It does not support other assets, Bitcoin runes, other releases, reverse-direction deposits or arbitrary bridge names. The target rsERG identities and nine-decimal unit scale are pinned, not inferred from metadata names.

The application page accepts an explicit deposit box ID; shared `?box=ID` links only fill the form. Box/transaction integrations recognize the same format. Loading a box does not trace it. **Inspect Rosen workflow** makes at most four same-origin reads: deposit creation transaction, exact R5 register lookup, one unambiguous event spend when present, and a second creation-transaction read to reject a changed deposit inclusion. Nothing polls or retries automatically. No request contacts Rosen or another chain. A destination explorer link contacts that third party only when opened.

## Interpretation and trust boundaries

From a confirmed, anchored source transaction, Kadia reconstructs the complete 12-field R5 event constant: source transaction ID, source chain, destination chain, declared source address, recipient, amount, bridge fee, network fee, source asset, target asset, source block ID and source height. Amounts/fees/heights use eight-byte big-endian integers in the event. Monetary arithmetic uses `BigInt`; decimal strings never pass through floating point.

`/v1/registers/R5/{constant}/boxes?consistency=strict&limit=10&dir=desc` finds only exact serialized matches. A result is recognized only with the pinned Ergo trigger script, Ergo RWT token, 32-byte WID digest, pinned permit-script digest and bounded positive declared commitment count. This is observed indexed structure, not independent verification of watcher signatures or quorum. Extra matching-register boxes with other contracts are disclosed as rejected candidates. Multiple matches or a continuation withhold a single spend interpretation. Zero matches means no supported event in that result, not rejection or non-observation across all bridge services/history.

For exactly one complete event result, the spending transaction must reference the same immutable event box and recorded spend height. A pinned first permit output plus a resolved bridge-lock input is labelled **reward-distribution-shaped**. The first parseable non-permit R4 can supply a recorded target transaction ID; it is not independently verified payment evidence. A pinned first fraud output is labelled **cleanup-shaped**, without inferring malicious intent, failure of all related events, or nonpayment. Other spends remain unknown. No claim is made about the signature branch, guard honesty, external finality, final recipient amount or fee sufficiency.

The lookup anchor is displayed. Reads are separate snapshots; the source inclusion is rechecked before publication, not represented as one atomic cross-chain view. Explicit refresh clears previous results immediately; timeout, mismatch and request failure cannot preserve a success indicator. Changing the deposit or leaving the view cancels requests and discards late responses. The interface does not imply a loaded observation is live.

Limits: 100 combined transaction inputs/outputs, ten event candidates, 2 MiB per received JSON response, 20 seconds for an inspection, 2 KiB serialized register bytes, 512 bytes per byte-array field. Native Ergo amounts and declared fees are positive/nonnegative signed-Long quantities; a deposit whose declared fees consume its entire value is outside supported scope. Address format screening does not establish checksum validity, ownership or destination acceptance.
