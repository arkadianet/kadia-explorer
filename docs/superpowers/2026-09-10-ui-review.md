Computed contrast from the actual rendered controls: menu text **15.74:1 light / 16.34:1 dark** against its ink surface; green focus outline and active More text **6.93:1 / 8.35:1**. Heading text is **16.77:1 / 14.23:1** against its existing surface. Keyboard regression assertions require text contrast ≥4.5:1, outline contrast ≥3:1, and a solid 2px focus outline on menu links. At 320px, the More button measured approximately **59.2×50.75px**; disclosure links are at least 44px tall. The disclosure uses a button with `aria-expanded` and `aria-controls`, ordinary navigation links, and a hidden region when closed.

**Rejected work and limits on the scores**

The first implementation used native `details` with a bound open state. It scored **7/10**: the new keyboard test exposed an open/close synchronization failure when Escape was followed by reopening. I removed that implementation and replaced it with explicit disclosure state; all six keyboard/theme/breakpoint tests now pass. The failing implementation is not retained.

Did not use ellipsis to conceal the long heading: it would hide the very data the detail page exists to show. Did not add virtualization or rewrite pagination based solely on large total counts: real initial rendering stayed bounded, and the 50→100 holder-page test passed. Sustained scrolling through an entire history has not been validated and is not claimed to have constant memory use.

No screenshots were used to infer aesthetic quality. Maximum protocol-size boxes/registers, all possible Unicode controls, physical touch devices, screen-reader speech, Safari/Firefox, 200% zoom, and full-history scrolling remain unverified. The delayed-request test covers holders; it does not establish that every existing route remains responsive under every slow mandatory metadata request. No claim is made that the whole pre-existing UI now meets every accessibility criterion.

**Performance measurement**

Compared a clean production build of original commit `3802ace` in an isolated temporary directory against the final production build. Both preview servers used the same read-only mainnet API. Headless Chromium used fresh 320×900 pages, alternated before/after order, and measured browser `first-contentful-paint`. Twelve samples per route/version were collected; the first two were discarded as warm-up. No test suite or build ran concurrently with the final comparison.

| Route | Before median | After median | Before p90 | After p90 |
| --- | ---: | ---: | ---: | ---: |
| Home | 160ms | 156ms | 172ms | 180ms |
| Long-name token | 124ms | 120ms | 132ms | 132ms |

There is no meaningful measured first-paint regression; the 4ms median differences and 8ms Home p90 increase are within a display frame and are not evidence of a speedup. This is a local-machine sample, not a WAN performance guarantee. Encoded JS resource bytes measured by the browser were 55,481→55,796 on Home and 55,053→55,415 on the token page. DOM elements increased by 11 and 12 respectively. The final build's bundle-budget result was **58.95KB gzipped**, under the existing 120KB budget.
